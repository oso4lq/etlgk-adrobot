# Adrobot — обёртка над Keitaro

Этот файл — рабочий контекст для Claude Code. Читай его целиком в начале каждой сессии.
Здесь только понятия и правила, без кода. Реализация — на тебе, но в рамках этих правил.

---

## 1. Как работать

- Перед написанием кода на каждом этапе сначала составь короткий план и дождись подтверждения владельца репозитория. Используй плагин superpowers для планирования работы.
- Работай этапами (см. раздел 10). Один этап — один законченный кусок с тестами и отдельным коммитом. К следующему этапу не переходи, пока тесты текущего не зелёные.
- Не выдумывай устройство Keitaro API. Пути, поля и форматы запросов берутся только из `docs/` (примеры реальных запросов, спецификация Swagger) или из проверенного реального ответа API. Если чего-то нет — остановись и спроси.
- Если в требованиях неоднозначность (см. раздел 11) — выбери решение с наименьшим сюрпризом для пользователя, запиши его в `docs/decisions.md` и упомяни в итоговом сообщении этапа.
- Секреты (ключ API, адрес трекера) — только в `.env`. В репозиторий попадает только `.env.example`. Ключ никогда не печатается в логах и не попадает в ответы API.
- Небольшие, читаемые коммиты. Сообщения коммитов — по делу.

## 3. Задача

Две части:

1. **Создаватор кампаний.** Принимает название кампании, гео-код страны и ID оффера Keitaro. Создаёт в Keitaro кампанию с двумя потоками:
   - первый поток ловит всех из указанной страны и редиректит на google.com;
   - второй поток получает всех остальных и отправляет на выбранный оффер.
   У кампании настроены домен, группа и источник (значения фиксированы конфигурацией, в Keitaro они есть как справочники). Интерфейс: поля Name, Geo (список кодов стран), Offer (поиск с автокомплитом), кнопка Create.
2. **Редактор существующей кампании.** Повторяет логику уже существующей «обёртки» (раздел 6): получение потоков, добавление и удаление офферов, пересчёт весов, закрепление весов, черновики и публикация в Keitaro.

## 4. Стек

- Бэкенд: FastAPI, SQLAlchemy 2.x, Alembic, Pydantic v2, httpx для обращений к Keitaro, pytest (+ мок HTTP для Keitaro).
- БД: SQLite по умолчанию (запуск без лишних зависимостей), строка подключения через конфиг, чтобы можно было подставить Postgres.
- Фронтенд: актуальный Angular (20+), standalone-компоненты, signals, новый синтаксис потока управления, TypeScript в строгом режиме.
- Менеджер пакетов фронта: pnpm.

## 5. Часть 1 — создаватор: правила

- Keitaro остаётся источником истины. Создание кампании — это несколько последовательных обращений к Keitaro (кампания, затем два потока). Если процесс упал посередине, нужна компенсация: убрать за собой частично созданное и записать ошибку в журнал.
- Порядок потоков важен: поток с фильтром по стране стоит первым, поток «все остальные» — вторым.
- Идентификатор (alias) кампании генерируется случайной короткой строкой, как в примерах Keitaro.
- Домен, группа и источник берутся из конфигурации (по имени или id), а не хардкодятся в логике.
- Валидация до обращения к Keitaro: код страны из допустимого списка, оффер существует, имя не пустое.
- В ответе пользователю: что создано, id кампании, ссылка/идентификатор кампании.
- Все созданные приложением кампании фиксируются в нашей БД (журнал).

## 6. Часть 2 — редактор: предметная область и поведение

Основа — транскрипция видео. Здесь она пересказана в виде правил. При расхождении приоритет у транскрипции.

### 6.1. Идея

Обёртка хранит **локальное представление** потоков кампании и их офферов в нашей БД. Пользователь меняет локальное представление (это черновик), и только по кнопке **Push to KT** изменения публикуются в Keitaro. До публикации Keitaro не меняется: если обновить страницу, Keitaro по-прежнему показывает старое состояние.

### 6.2. Сущности (на уровне понятий)

- **Кампания** — привязана к кампании Keitaro.
- **Поток** — принадлежит кампании, имеет id из Keitaro. Бывает двух видов:
  - поток с офферами — показываем офферы и работаем с ними;
  - поток без офферов — показываем просто как поток, без каких-либо данных о редиректах и фильтрах. Эта информация нам не нужна, содержимое такого потока не разбираем и не трогаем.
- **Привязка оффера к потоку** — запись в нашей БД: какой оффер, в каком потоке, какой вес, закреплён ли вес, в каком состоянии. Сам оффер живёт в Keitaro; при отмене удаляется только привязка, оффер остаётся.
- **Состояние потока** — «чистый» (совпадает с Keitaro, отображается белым) или «черновик» (есть неопубликованные изменения, отображается жёлтым).
- **Состояния привязки оффера:**
  - активный — оффер в потоке, есть в Keitaro;
  - добавленный, но не опубликованный;
  - удалённый — серый, вес 0%, лежит в «архиве» потока, может быть возвращён.

### 6.3. Сценарии

1. **Fetch Streams.** Получаем из Keitaro все потоки выбранной кампании и их офферы, обновляем локальное представление (правила синхронизации — 6.5).
2. **Добавление оффера.** Выбор оффера через поиск (по ID, желательно и по названию; поиск идёт через нашу API в API Keitaro). После добавления:
   - веса всех незакреплённых офферов потока пересчитываются, итог всегда 100%;
   - поток становится жёлтым;
   - в Keitaro пока ничего не меняется.
3. **Push to KT.** Публикует изменения потока в Keitaro: актуальный состав офферов и их веса. Поток становится белым. Нужно менять только офферы потока, остальные настройки потока (фильтры, действие, прочее) трогать нельзя — проверь это реальным запросом.
4. **Cancel.** Для неопубликованного потока откатывает черновик: офферы, добавленные до публикации, удаляются из нашей БД (удаляется привязка, сам оффер в Keitaro остаётся), поток снова белый, как будто изменений не было.
5. **Remove.** Любой оффер можно убрать из потока. Оффер становится серым, вес 0%, поток жёлтый. После публикации оффер исчезает из Keitaro, но остаётся у нас в архиве потока серым.
6. **Bring back.** Для удалённого оффера возвращает его в поток: поток снова жёлтый, после публикации оффер возвращается в Keitaro. Веса пересчитываются по общим правилам.
7. **Закрепление веса (pin).** Вес оффера можно закрепить. Дальше любое добавление, удаление или возврат офферов пересчитывает веса всех офферов, кроме закреплённых.
8. **Удаление в самом Keitaro.** Если пользователь удалил офферы прямо в Keitaro и затем снова нажал Fetch Streams, известные нам офферы, которых в Keitaro больше нет, не пропадают, а переходят в состояние «удалён» (серые, с кнопкой Bring back) — как будто их убрали руками в обёртке.

### 6.4. Правила весов (это ядро, покрыть тестами в первую очередь)

- Сумма весов активных офферов потока всегда 100%.
- Закреплённые веса не меняются при пересчёте.
- Остаток (100 минус сумма закреплённых) делится поровну между незакреплёнными активными офферами. Пример из видео: четыре оффера без закреплённых — по 25% каждому. Пример с закреплением: закреплён вес 25%, возвращаем оффер — закреплённый остаётся 25%, оставшиеся два делят остальное поровну.
- Удалённые офферы не участвуют в расчёте и показываются с 0%.
- Расчёт весов — отдельная чистая функция без обращений к БД и сети, чтобы её можно было тестировать изолированно.

### 6.5. Синхронизация (Fetch Streams)

- Оффер есть и в Keitaro, и у нас — остаётся активным, вес берётся из Keitaro.
- Оффер есть в Keitaro, но мы про него не знали — добавляется как активный.
- Оффер у нас есть, в Keitaro его больше нет — переходит в «удалён».
- Потоки без офферов добавляются как простые потоки, без разбора содержимого.
- Что делать с потоком, у которого есть неопубликованный черновик (раздел 11).

## 7. Архитектура

- Слои: роутеры (только HTTP и валидация) → сервисы (бизнес-логика, правила весов, синхронизация, публикация) → клиент Keitaro (единственное место, где знают про формат Keitaro) → репозитории (работа с БД).
- Клиент Keitaro изолирован за интерфейсом, чтобы в тестах подменять его моком.
- Схемы запросов и ответов нашей API — свои, не копия схем Keitaro.
- БД хранит: журнал созданных кампаний, локальное представление потоков и привязок офферов (состояние, вес, закрепление), при необходимости кэш офферов для автокомплита.
- Миграции — только через Alembic, откат и накат должны работать. Любое изменение схемы БД — новая миграция.
- Ошибки Keitaro (недоступен, неверный ключ, невалидные данные) превращаются в понятные ответы нашей API, а не в «500».
- Таймауты и повторные попытки при обращении к Keitaro — разумные и настраиваемые.

## 8. Правила кода

### Общие
- Читаемость важнее краткости. Имена — осмысленные, без сокращений. Бизнес-логика не живёт в роутерах и компонентах.
- Каждая ветка поведения из раздела 6 покрыта тестом. Особый приоритет: расчёт весов, переходы состояний, синхронизация.
- Комментарии объясняют «почему», а не «что».

### TypeScript (файлы .ts)
- Предпочитай циклы `for...of` / `for...in` цепочкам `.filter` + `.map`.
- Не используй методы Object (keys, values, entries и т. п.), если нужен доступ к одному-двум конкретным свойствам, есть конкретный ключ для поиска, можно обратиться по индексу напрямую или типы известны на этапе компиляции.
- Принцип выбора: прямой доступ — когда знаешь, ЧТО ищешь; методы Object — когда нужно обработать ВСЁ подряд.

### Angular, HTML-шаблоны
- Только блоки нового синтаксиса: @if, @else, @for, @switch, @case. Устаревшие ngIf, ngFor и подобные не использовать.
- Шаблоны декларативные, не императивные: в них подставляются заранее подготовленные или вычисленные данные (signals, computed).
- В шаблонах не вызывать методы и геттеры. Всё, что нужно для отображения (цвет потока, подписи, состояния кнопок, веса в процентах), подготавливается заранее в компоненте или сервисе.
- Компоненты standalone, состояние — на signals, интерфейс минималистичный: важна работа кнопок и верность цифр, а не оформление.

## 9. Осторожность с реальным Keitaro

- Keitaro — реальная система. Создавай и меняй только то, что создано этим приложением или явно указано владельцем.
- Никогда не удаляй и не изменяй чужие кампании, потоки, офферы, домены, группы и источники.
- Для проверок против реального Keitaro используй тестовые кампании с понятным префиксом в названии.
- Публикация в Keitaro меняет только офферы нужного потока. После первой такой проверки убедись, что остальные настройки потока не изменились.
- Тебе разрешён доступ в реальный Keitaro, используй Playwright MCP. Адрес, логин и пароль админки — в `.env` (`KEITARO_BASE_URL` + `/admin`, `KEITARO_ADMIN_LOGIN`, `KEITARO_ADMIN_PASSWORD`). В репозиторий они не попадают.
- Документация к API и ключ — в админке Keitaro.

## 11. Открытые вопросы (решить и записать в `docs/decisions.md`)

- **Округление весов.** Если проценты целые, остаток от деления нужно распределять детерминированно, чтобы сумма всегда была ровно 100%.
- **Крайние случаи закрепления.** Сумма закреплённых весов ≥ 100%, все офферы закреплены, закреплённые не дают в сумме 100% при отсутствии незакреплённых. Нужно поведение и сообщение пользователю.
- **Fetch Streams при наличии черновика.** Предложение по умолчанию: не затирать неопубликованные изменения молча, а предупредить пользователя.
- **Cancel и удаления.** В видео показан откат добавленных офферов. Предположение: Cancel откатывает весь черновик потока, включая неопубликованные удаления и возвраты.
- **Добавление оффера в поток без офферов.** По умолчанию добавляем офферы только в потоки, где они уже есть.
- **Выбор кампании в редакторе.** Список кампаний из Keitaro с поиском или ввод ID.
