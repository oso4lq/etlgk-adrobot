# Этап 4 — фронтенд на Angular и демо-стенд: дизайн

Дата: 2026-11-24. Статус: черновик, на согласовании у владельца.
Основа: `CLAUDE.md` (разделы 3, 6, 8, 10), общий дизайн `docs/superpowers/specs/2026-11-18-adrobot-design.md` (раздел 7), `docs/decisions.md`, API бэкенда этапов 2–3 (`backend/app/api/`, `backend/app/schemas/`).

## 1. Зачем

Бэкенд создаватора и редактора готов (этапы 2–3). Пользователю нужен интерфейс: страница создания кампании и страница редактора, на которой повторяется ролик из `docs/video-transcript.md`: Fetch Streams, добавление оффера, Push to KT, Cancel, Remove, Bring back, Pin.

Критерий готовности этапа (раздел 10 `CLAUDE.md`): все кнопки работают, веса на экране в сумме дают 100%.

Проверить это на реальном Keitaro сейчас нельзя, а полностью — нельзя в принципе:
- с 2026-11-23 Admin API трекера отвечает 403 на любые запросы с этой машины (повторно проверено 2026-11-24 командой разведки);
- даже с доступом тестовому пользователю виден один оффер (18813), а сценарий из видео требует трёх-четырёх.

Поэтому вместе с фронтендом делается **демо-стенд**: бэкенд с Keitaro в памяти, заполненным как в видео (выбор владельца).

## 2. Цели, не-цели, анти-цели

**Цели**
- Страница **Create**: Name, Geo, Offer (поиск с автокомплитом), Create; результат или понятная ошибка.
- Страница **Editor**: выбор кампании с поиском, Fetch Streams, потоки белые и жёлтые, офферы активные и серые (архив), добавление с поиском, Remove, Bring back, Pin, Unpin, Push to KT, Cancel.
- Все сценарии ролика проходятся в браузере на демо-стенде, суммы весов на экране — 100%.
- Код соответствует разделу 8 `CLAUDE.md` (шаблоны без вызовов методов, `@if/@for`, signals, `for...of`).

**Не-цели**
- Изменение API бэкенда. Фронтенд работает с тем, что есть. Если чего-то не хватит — остановиться и согласовать отдельно.
- Оформление сверх минимального: важны работа кнопок и верность цифр (`CLAUDE.md`, раздел 8).
- Ручной ввод веса, редактирование фильтров и потоков, авторизация (не-цели общего дизайна).
- Сквозные автотесты в репозитории (Playwright как зависимость проекта). Проход по ролику — вручную через Playwright MCP, результат записывается (раздел 9).
- README и Docker — этап 5.

**Анти-цели** (провал, даже если «работает»)
- Цифры на экране расходятся с ответом API: фронтенд сам пересчитывает веса или угадывает состояние. Веса и состояния берутся только из ответа бэкенда.
- Двойное нажатие отправляет два запроса (например, два Push или два добавления).
- Fetch молча теряет черновик: отброс черновиков — только явным подтверждением пользователя.
- Демо-стенд обращается к настоящему Keitaro или читает `.env` с ключом.
- Код демо-стенда попадает в приложение (`backend/app/`) или фронтенд знает о демо-маршрутах.

## 3. Ограничения

- Angular 22.2 (установлен), standalone, signals, zoneless (по умолчанию в каркасе), strict TS, pnpm. Node 24.16.0 (`frontend/.nvmrc`, `nvm use 24.16.0`).
- Тесты — vitest через `ng test` (каркас этапа 0). Линтер — `ng lint` (angular-eslint; правило `prefer-control-flow` уже включено).
- Dev-сервер проксирует `/api` на `http://localhost:8000` (`frontend/proxy.conf.json`).
- Формат ошибок API — `{"code", "message"}`, тексты уже на русском (таблица кодов — `docs/decisions.md`, этапы 2–3).
- Без UI-библиотек (Angular Material и т. п.): интерфейс минималистичный, лишние зависимости не нужны.

## 4. Подходы

### 4.1. Устройство фронтенда

| Подход | Суть | Плюсы | Минусы |
|---|---|---|---|
| **A. Хранилище на signals + чистые мапперы** (выбран владельцем) | Тонкие API-сервисы на `HttpClient` → хранилище страницы со состоянием в signals → чистая функция «ответ API + состояние UI → view-model» → `computed` → компоненты только отображают | Логики в компонентах нет; мапперы тестируются без Angular; прямо следует `CLAUDE.md` и разделу 7 общего дизайна | Кода чуть больше |
| B. `httpResource` в компонентах | Компонент сам грузит данные и реагирует на ответы | Меньше кода | Ошибки, блокировка кнопок и подготовка данных расползаются по компонентам; хуже тестируется; против правила «бизнес-логика не живёт в компонентах» |
| C. NgRx SignalStore | Готовая библиотека хранилищ | Привычный шаблон | Лишняя зависимость без выигрыша на двух страницах |

### 4.2. На чём проверять работу кнопок

| Подход | Суть | Итог |
|---|---|---|
| **A. Демо-стенд** (выбран владельцем) | Скрипт запускает бэкенд с фейковым Keitaro в памяти, заполненным как в видео | Весь ролик проходится в браузере; пригодится для ручного прогона на этапе 5 |
| B. Только реальный Keitaro | Ничего лишнего | Сейчас заблокировано 403; даже с доступом — только сценарии с одним оффером |

## 5. Дизайн: страницы и поведение

### 5.1. Маршруты и каркас

- `/` → перенаправление на `/create`.
- `/create` — страница создания.
- `/editor` — редактор без выбранной кампании (только выбор).
- `/editor/:campaignId` — редактор кампании. Id в адресе: после обновления страницы открыта та же кампания.
- В шапке (`App`) — заголовок Adrobot и ссылки Create / Editor.

### 5.2. Язык интерфейса

Названия элементов управления — как в постановке и в видео, по-английски: Name, Geo, Offer, Create, Fetch Streams, Push to KT, Cancel, Remove, Bring back, Pin, Unpin, Add. Остальной текст (заголовки, подсказки, состояния) — по-русски, как и сообщения бэкенда. *(Решение исполнителя: кнопки узнаются по ролику, сообщения API уже русские.)*

### 5.3. Страница Create

Поля:
- **Name** — текстовое поле, обязательное (не пустое после обрезки пробелов), не длиннее 255 символов.
- **Geo** — `<select>` со странами из `GET /api/countries`, подпись «AU — Australia», порядок — как отдаёт API.
- **Offer** — автокомплит (5.5) по `GET /api/offers?query=`, подпись «18813 — название». Оффер выбирается только из списка подсказок.
- **Create** — неактивна, пока форма не заполнена или идёт запрос.

Форма — на Signal Forms (`@angular/forms/signals`, в Angular 22 стабильны). Проверки на клиенте — только очевидные (заполненность, длина), полную проверку делает бэкенд.

После `POST /api/campaigns`:
- **успех** — блок «Кампания создана»: название, id в Keitaro, alias, ссылка кампании (`campaign_url`), страна, оффер, id обоих потоков и ссылка «Открыть в редакторе» → `/editor/{id}`. Форма очищается.
- **ошибка** — текст `message` из ответа рядом с кнопкой; введённые значения не теряются.

Под формой — **журнал созданных кампаний** (`GET /api/created-campaigns`): дата, название, страна, оффер, статус, id в Keitaro, текст ошибки. Обновляется после каждой попытки создания. Статус `compensation_failed` выделен: такая кампания требует ручной уборки. *(Решение исполнителя: эндпоинт уже есть, а неудачные попытки иначе не видны пользователю.)*

### 5.4. Страница Editor

**Выбор кампании** — автокомплит по `GET /api/keitaro-campaigns?query=` (подпись «id — имя»). Выбор ведёт на `/editor/{id}`.

**Открытие кампании** (`/editor/:campaignId`) — `GET /api/editor/campaigns/{id}`:
- 200 — показываем кампанию;
- 404 `campaign_not_fetched` — «Кампания {id} ещё не загружена в редактор» и кнопка Fetch Streams;
- прочие ошибки — текст ошибки на месте списка потоков.

**Шапка кампании**: имя, id в Keitaro, время последнего Fetch (локальное время, формат готовит маппер). Если `write_allowed = false` — пометка «Публикация в эту кампанию запрещена (защита по префиксу)».

**Fetch Streams** — `POST /api/editor/campaigns/{id}/fetch`:
- `notices` из ответа показываются над потоками (например, потоки с потерянными черновиками);
- если `kept_draft_stream_ids` не пуст — сообщение «Черновики сохранены в потоках: …» и кнопка «Fetch Streams с отбросом черновиков». Она открывает подтверждение прямо на странице («Неопубликованные изменения в потоках … будут потеряны»; «Отбросить и загрузить» / «Отмена»). Подтверждение отправляет `fetch?force=true`. *(Решение исполнителя: окно браузера `confirm()` хуже тестируется и выглядит чужеродно.)*
- пока идёт Fetch, все кнопки страницы неактивны.

**Поток с офферами** (`has_offers = true`) — карточка:
- Заголовок: имя потока, id в Keitaro, пометка «черновик», если `is_draft`. Фон белый, у черновика жёлтый.
- **Таблица активных офферов**: «id — имя», вес «25%», пометка «закреплён» у закреплённого, пометка «не опубликован» у `is_published = false`. В строке — кнопки Remove и Pin (или Unpin, если закреплён).
- Строка итога: «Итого: N%» — сумма весов активных офферов из ответа. Если N ≠ 100 (и активные офферы есть), строка выделена.
- **Архив** (офферы со статусом `removed`): серые строки, вес «0%», кнопка Bring back. Блок скрыт, если архив пуст.
- **Проблемы** (`problems`, блокируют Push) и **предупреждения** (`warnings`) — списками под таблицей, тексты из ответа как есть.
- **Добавление**: автокомплит по `GET /api/offers?query=` и кнопка Add (активна, когда оффер выбран). В подсказках скрыты офферы, уже активные в этом потоке. Оффер из архива потока показывается в подсказках: бэкенд выполнит для него Bring back (`docs/decisions.md`, «Добавление оффера»).
- **Push to KT** активна, когда `can_push`; **Cancel** — когда `can_cancel`.

**Поток без офферов** — только имя, id и подпись «поток без офферов». Ни кнопок, ни добавления: добавлять можно только в потоки, где офферы уже есть (`docs/decisions.md`).

**Операции с потоком** (add, remove, bring back, pin, unpin, push, cancel):
- пока идёт запрос по потоку, все кнопки этого потока неактивны. Повторное нажатие не отправляет второй запрос;
- ответ — полный `StreamResponse`. Хранилище заменяет им поток в кампании, ничего не пересчитывая;
- ошибка — `message` показывается в карточке потока до следующего успешного действия с этим потоком. Состояние потока не меняется (бэкенд при ошибке не меняет БД).
- 409 `keitaro_stream_changed` при Push: текст бэкенда уже говорит «выполните Fetch Streams с отбросом черновика». Пользователь жмёт Fetch Streams, видит сохранённый черновик и кнопку отброса.

### 5.5. Автокомплит

Один общий компонент для трёх мест: оффер в Create, оффер при добавлении, выбор кампании.
- Вход: функция поиска `(query) => Observable<Option[]>`, где `Option = {id, label}`; необязательный набор id, которые не показывать.
- Ввод → задержка ~250 мс → запрос. Новый ввод отменяет предыдущий запрос.
- Выпадающий список подсказок; выбор мышью (клавиатура — по возможности). Выход — событие с выбранным `Option`.
- Очищается снаружи (после успешного Add или Create).
- Ошибка поиска — строка «Поиск недоступен: …» под полем.

## 6. Дизайн: устройство кода

### 6.1. Слои

```
src/app/
  core/       типы ответов API, разбор ошибок, общие утилиты
  shared/     автокомплит
  creator/    CreatorApi, CreatorStore, маппер, страница Create
  editor/     EditorApi, EditorStore, маппер, страница Editor, карточка потока
```

- **API-сервисы** (`CreatorApi`, `EditorApi`, `providedIn: 'root'`) — только HTTP: путь, параметры, тип ответа. Возвращают `Observable`.
- **Хранилища** (`CreatorStore`, `EditorStore`) — предоставляются на уровне компонента страницы, поэтому состояние сбрасывается при уходе со страницы. Внутри — signals и методы-действия. Только хранилища вызывают API.
- **Мапперы** — чистые функции без Angular: «ответ API + состояние UI → view-model». Всё, что видит пользователь, готовят они: подписи, проценты, CSS-класс цвета, видимость и доступность кнопок, деление на активные офферы и архив, итог, формат даты.
- **Компоненты** — показывают `computed` view-model и передают нажатия в хранилище. Карточка потока получает свой view-model через `input()` и сообщает о нажатиях через `output()`.

### 6.2. Состояние редактора (`EditorStore`)

Signals:
- `campaignId`;
- `campaign` — последний `CampaignResponse` или `null`;
- статус загрузки: idle / loading / not-fetched / ready / error, плюс текст ошибки страницы;
- результат последнего Fetch: `notices`, `kept_draft_stream_ids`;
- идёт ли Fetch; открыто ли подтверждение принудительного Fetch;
- id потоков, по которым идёт запрос;
- ошибка последнего действия по каждому потоку.

`view = computed(() => toEditorView(...))`. Действия: `open(id)`, `fetch()`, `askForceFetch()`, `confirmForceFetch()`, `dismissForceFetch()`, `addOffer`, `removeOffer`, `bringBack`, `pin`, `unpin`, `push`, `cancel`.

### 6.3. Ошибки HTTP

Одна функция превращает `HttpErrorResponse` в `{code, message}`:
- тело `{code, message}` — как есть;
- статус 0 — «Бэкенд недоступен»;
- иное тело — «Неожиданный ответ сервера (HTTP N)».

### 6.4. Правила шаблонов (раздел 8 `CLAUDE.md`)

- Только `@if`, `@for`, `@switch`. Это уже проверяет линтер.
- Отображаемые значения — только поля готового view-model. Никаких вызовов методов, геттеров, пайпов и вычислений в шаблоне.
- Чтение signal (`view()`) разрешено: signals — обязательный по `CLAUDE.md` способ хранить состояние, а чтение ничего не вычисляет. *(Решение исполнителя, записать в `docs/decisions.md`.)*
- Обработчики событий (`(click)="…"`) вызывают методы хранилища: это реакция на действие пользователя, а не подготовка данных для отображения. *(Решение исполнителя, записать.)*
- TS: `for...of` вместо цепочек `.filter().map()`; методы `Object` — только когда нужно обойти всё подряд.

## 7. Дизайн: демо-стенд

- Модуль `backend/tools/demo_stand.py`, запуск из `backend/`: `python -m tools.demo_stand [--port 8000]`. Порт по умолчанию 8000 — тот, на который смотрит прокси фронтенда, поэтому фронтенд запускается как обычно (`pnpm start`).
- Приложение собирается через `create_app(settings, keitaro_client=фейк)`. Фейк — `FakeKeitaroClient` из `backend/tests/fakes.py`, один на тесты и стенд, без копии. *(Решение исполнителя.)*
- Настройки задаются в коде (`.env` не читается), ключ и адрес — заведомо фиктивные. Справочники создаватора — те, что есть в фейке (`kylovoa.com`, `FORTESTS`), поэтому страница Create на стенде тоже работает. Префикс записи — `test_oso4lq_`, как в настоящем `.env`.
- База — отдельный SQLite-файл стенда. При каждом запуске создаётся заново и мигрируется через Alembic (`upgrade head`). Почему: фейковый Keitaro живёт в памяти и при перезапуске возвращается к исходному состоянию — старая база с ним разошлась бы.
- **Начальные данные** (как в видео):
  - кампания `test_oso4lq_demo_video`: Flow 1 «Australia → Google» (без офферов) и Flow 2 с тремя офферами, доли 34/33/33;
  - в каталоге офферов — эти три и ещё три-четыре для добавления;
  - чужая кампания без префикса (один поток с офферами) — чтобы увидеть, что Push туда запрещён.
- **Демо-маршруты** добавляются только в приложение стенда, под `/demo` (не `/api`, поэтому фронтенд-прокси их не видит; вызываются из `/docs` или запросом):
  - `GET /demo/keitaro/streams/{id}` — что сейчас лежит «в Keitaro»: офферы и доли, а также тип, схема, тип действия и состояние потока — всё, что хранит модель потока (`backend/app/keitaro/models.py`). Фильтров и адреса редиректа в модели нет, и добавлять их в код приложения ради стенда не будем. Доказательство «Push меняет только офферы» — реальный запрос этапа 1 (`docs/decisions.md`, В3) и живая проверка этапа 3, а не стенд: фейк по устройству меняет только офферы. *(Решение исполнителя.)*
  - `POST /demo/keitaro/streams/{id}/offers/{offer_id}/delete` — удалить оффер из потока «в админке Keitaro» (сценарий 8 видео).
- При запуске в консоль печатается, что это демо-стенд без настоящего Keitaro, и адреса: API, `/docs`, демо-маршруты.
- Тесты стенда (pytest): начальные данные, оба демо-маршрута, ответ `GET /api/editor/...` после Fetch на стенде.

## 8. Тестирование

Фронтенд (`ng test`, vitest), по приоритету:
1. **Мапперы редактора** — таблица случаев: белый и жёлтый поток; поток без офферов; активные, закреплённые, неопубликованные и удалённые офферы; итог 100 и не 100; доступность кнопок от `can_push`/`can_cancel` и от «идёт запрос»; ошибка потока; подтверждение принудительного Fetch.
2. **`EditorStore`** с `HttpTestingController`: открытие (200, 404 `campaign_not_fetched`, ошибка); Fetch с черновиками → подтверждение → `force=true`; действие заменяет поток ответом; ошибка действия записывается в поток и снимает «идёт запрос»; второе нажатие во время запроса не отправляет запрос.
3. **Разбор ошибок HTTP** — три ветки из 6.3.
4. **`CreatorStore` и маппер Create**: успех (результат, обновление журнала, очистка формы), ошибка (текст, значения сохранены), неактивная кнопка.
5. **Автокомплит**: задержка, отмена предыдущего запроса, скрытые id, выбор.
6. **Компоненты — минимально**: карточка потока (жёлтый класс, неактивные кнопки, архив), страница Create (поля на месте).

Плюс `ng lint` и `ng build` без ошибок, `pytest` и `ruff` бэкенда зелёные.

## 9. Приёмка

На демо-стенде через Playwright MCP проходится ролик. На каждом шаге, где веса считает обёртка, итог потока — 100%; «Keitaro» проверяется через `GET /demo/keitaro/streams/{id}`:

1. Editor → выбрать `test_oso4lq_demo_video` → Fetch Streams: Flow 1 — простой поток, Flow 2 — три оффера 34/33/33, оба белые.
2. Add оффер → 25/25/25/25, поток жёлтый, оффер «не опубликован»; «в Keitaro» по-прежнему три.
3. Push to KT → поток белый; «в Keitaro» четыре по 25; тип, схема, тип действия и состояние потока не изменились.
4. Add ещё один → Cancel → оффер исчез, веса прежние, поток белый.
5. Remove → оффер серый, 0%, в архиве, поток жёлтый → Push → «в Keitaro» его нет, у нас он серый в архиве.
6. Bring back → поток жёлтый → Push → оффер снова «в Keitaro».
7. Удалить два оффера демо-маршрутом → Fetch Streams → они серые, с Bring back, поток белый. Оставшиеся два — по 25%, как в Keitaro: Fetch берёт веса как есть (`docs/decisions.md`). Поэтому итог 50% выделен и видна проблема «Сумма весов 50%, нужно 100% — веса пересчитаются при добавлении, удалении или возврате оффера». Так и должно быть: экран честно показывает состояние Keitaro после ручной правки. Демо-маршрут доли не пересчитывает, иначе шаг 8 пошёл бы не как в видео.
8. Pin оффера с 25% → Bring back одного из удалённых → закреплённый остался 25%, два других поделили 75% (38/37), итог 100%, проблема исчезла → Push → «в Keitaro» те же веса.

Дополнительно:
- Fetch Streams при черновике → черновик сохранён → отброс с подтверждением.
- Push в чужую кампанию стенда запрещён (кнопка неактивна, проблема видна).
- Create на стенде → результат, запись в журнале, «Открыть в редакторе» → Fetch Streams.

Результат прохода записывается в `docs/decisions.md` (раздел этапа 4): что проверено и чем.

Живая проверка этапа 3 на реальном Keitaro не входит в приёмку этапа 4. Если доступ к Admin API вернётся во время этапа, она выполняется по плану этапа 3 (задача 12), а затем короткий проход по UI на кампании `test_oso4lq_`.
