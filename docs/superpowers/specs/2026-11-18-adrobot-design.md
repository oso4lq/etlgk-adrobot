# Adrobot — дизайн

Дата: 2026-11-18. Статус: согласован владельцем 2026-11-18.
Источники: `CLAUDE.md`, `docs/video-transcript.md`, скриншоты постановки, `docs/keitaro-openapi.json`, разведка реального Keitaro (только чтение, 2026-11-18).

## 1. Зачем

Обёртка над трекером Keitaro из двух частей:

1. **Создаватор** — по имени, коду страны и офферу создаёт в Keitaro кампанию из двух потоков (страна → google.com, остальные → оффер) с доменом, группой и источником из конфигурации.
2. **Редактор** — повторяет существующую обёртку из видео: локальная копия потоков и офферов кампании, черновики (жёлтый поток), пересчёт и закрепление весов, архив удалённых офферов, публикация в Keitaro по кнопке.

Контекст: это тестовое задание, работа идёт на общем инстансе Keitaro, где одновременно работают другие кандидаты (~400 чужих кампаний `test_<фамилия>_…`). Поэтому осторожность с чужими объектами — жёсткое требование, а не пожелание.

## 2. Цели, не-цели, анти-цели

**Цели**
- Все сценарии из видео (раздел 6.3 `CLAUDE.md`) работают и покрыты тестами.
- Веса на экране и в Keitaro всегда сходятся в 100% (для потоков, изменённых через обёртку).
- Кампания из создаватора совпадает по структуре с эталоном (раздел 4.2).
- Понятные ошибки вместо «500» при любых проблемах с Keitaro.

**Не-цели**
- Ручной ввод веса оффера. В видео вес только закрепляется в текущем значении; поля ввода нет.
- Любое редактирование фильтров, действий, лендингов потоков; создание и удаление потоков в редакторе.
- Управление самими офферами, доменами, группами, источниками (только чтение справочников).
- Авторизация пользователей обёртки, многопользовательская работа, блокировки.
- Статистика (клики, конверсии).

**Анти-цели** (провал, даже если «работает»)
- Изменение чужих кампаний, потоков, офферов в общем Keitaro.
- Push, который меняет у потока что-то кроме офферов и их весов.
- Молчаливая потеря данных: затирание черновика при Fetch или перезапись ручных правок в Keitaro при Push.
- Ключ API или доступы в логах, ответах API, репозитории.
- Использование `clean_archive` — эта операция чистит архив всех пользователей инстанса.

## 3. Ограничения

### 3.1. Технологии (из `CLAUDE.md`)
- Бэкенд: Python, FastAPI, SQLAlchemy 2.x, Alembic, Pydantic v2, httpx, pytest. Локально Python 3.14; целимся в `>=3.12`.
- БД: SQLite по умолчанию, строка подключения в конфиге (`DATABASE_URL`), чтобы подставить Postgres.
- Фронтенд: актуальный Angular (20+), standalone, signals, новый control flow, strict TS, pnpm. Используется Angular 22, ему нужен Node ≥ 22.22.3 или ≥ 24.15 (локально — 24.16.0 через nvm, см. `frontend/.nvmrc`; поправлено на этапе 0).
- Правила кода и шаблонов — раздел 8 `CLAUDE.md` (обязательны).

### 3.2. Факты о Keitaro (проверены 2026-11-18)
- Admin API v1: `{KEITARO_BASE_URL}/admin_api/v1`, авторизация заголовком `Api-Key`. Версия трекера 10.x. Спецификация — `docs/keitaro-openapi.json`.
- Ключ создан в профиле тестового пользователя (id ключа 297), лежит только в `.env`.
- Права тестового пользователя: видит **1 оффер** (18813), **1 домен** (`kylovoa.com`, id 1813), **1 источник** (`FORTESTS`, id 836), 16 групп кампаний (нужная — `FORTESTS`, id 10332). Создавать офферы нельзя (403).
- `share` оффера в потоке — **целое число**.
- `GET /offers` не умеет искать — только полный список.
- `DELETE /campaigns/{id}` и `DELETE /streams/{id}` переносят в архив (не удаляют насовсем).
- `PUT /streams/{id}`: схема тела в спецификации пустая — какие поля можно слать частично и заменяет ли список `offers` целиком, **не известно**. Проверяется реальным запросом на этапе 1 (раздел 9).
- Keitaro принимает в потоке id офферов, к которым у пользователя нет доступа, и даже несуществующие (видно по чужим кампаниям). Проверять оффер должны мы.
- В Keitaro 10 потоки типов `regular`/`forced` перетаскиваются, `default` — нет.

### 3.3. Проверка на реальном Keitaro
Решение владельца: вживую проверяем всё, что возможно с одним оффером 18813 (создание кампании, Fetch, Remove, Bring back, Push, неизменность фильтров потока). Сценарии с несколькими офферами и пересчётом весов покрываются тестами с подменённым клиентом Keitaro.

Все объекты, которые мы создаём в Keitaro, имеют префикс `test_oso4lq_`.

## 4. Создаватор

### 4.1. Вход и валидация (до любых обращений на запись)
- `name` — непустой после обрезки пробелов. Если задан `KEITARO_WRITE_NAME_PREFIX`, имя обязано с него начинаться (иначе 422 с понятным текстом).
- `country` — **один** код страны ISO 3166-1 alpha-2 из допустимого списка. Допустимый список — все коды ISO 3166-1 alpha-2 (отдаётся эндпоинтом для выпадающего списка).
- `offer_id` — существует среди офферов, видимых через API.

### 4.2. Что создаётся (эталон)
Эталон — скриншот постановки (у обоих потоков есть ручка перетаскивания → оба `regular`) и фактическая структура кампаний в этом Keitaro.

- **Кампания:** `name`, `alias` — случайная строка из 6 символов `[A-Za-z0-9]` (как `wVqN1R` в эталоне), `type=position`, `state=active`, `domain_id`, `group_id`, `traffic_source_id` из конфигурации; значения админки по умолчанию — `cost_auto=true`, `uniqueness_method=ip_ua`, `uniqueness_param=""`, `notes=""`. Остальные поля — значения Keitaro по умолчанию.
- **Поток 1** (`position=1`): `name="Flow 1"`, `type=regular`, `weight=100`, `comments=""`, `schema=redirect`, `action_type=http`, `action_payload=REDIRECT_URL` (по умолчанию `https://google.com`), `filters=[{name: country, mode: accept, payload: [CODE]}]`, `state=active`.
- **Поток 2** (`position=2`): `name="Flow 2"`, `type=regular`, `weight=100`, `comments=""`, `schema=landings`, без фильтров, `offers=[{offer_id, share: 100, state: active}]`, `state=active`.

Формат тел сверен с реальным API на этапе 1 (10, 12, 13). Поля админки по умолчанию добавлены 2026-11-19 после сравнения с эталоном `test_oso4lq_reference`, собранным руками в админке (23), и проверены реальным запросом (24): результат совпадает с эталоном поле за полем (`docs/decisions.md`, «этап 2»).

### 4.3. Последовательность и компенсация
1. Запись в журнал `created_campaigns` со статусом `pending` (до обращения к Keitaro — чтобы даже падение процесса оставило след).
2. `POST /campaigns`. Если Keitaro отверг alias как занятый — новый alias, до 3 попыток.
3. `POST /streams` (поток 1), затем `POST /streams` (поток 2). После каждого шага id созданного объекта сохраняется в журнал.
4. Успех → статус `created`.
5. Ошибка на шаге 3 → компенсация: в архив созданные потоки, затем кампания (`DELETE`). Статус `failed`, текст ошибки, результат компенсации. Если компенсация сама упала → статус `compensation_failed` и id оставшихся объектов в журнале для ручной уборки.
6. Повторные попытки только для чтения (GET) и сетевых ошибок до отправки запроса. Запросы на создание автоматически не повторяются — иначе дубли.

### 4.4. Ответ
id кампании в Keitaro, alias, имя, ссылка кампании (`{домен}{alias}`), id обоих потоков, страна и оффер.

### 4.5. Справочники из конфигурации
`CAMPAIGN_DOMAIN`, `CAMPAIGN_GROUP`, `CAMPAIGN_TRAFFIC_SOURCE` — имя или числовой id. Разрешаются в id через API при первом использовании и кэшируются. Если не найдено — понятная ошибка конфигурации (без обращений на запись). Значения для нашего `.env`: `kylovoa.com`, `FORTESTS`, `FORTESTS`.

## 5. Редактор

### 5.1. Модель данных (вариант A — две версии в строке привязки)

```
editor_campaigns: id, keitaro_campaign_id (unique), name, last_fetched_at
editor_streams:   id, campaign_id, keitaro_stream_id (unique), name, position, has_offers
stream_offers:    id, stream_id, keitaro_offer_id, offer_name, sort_order,
                  status (active|removed), weight (int), is_pinned (bool),
                  published_status (active|removed|NULL), published_weight (int|NULL)
                  unique(stream_id, keitaro_offer_id)
created_campaigns (журнал создаватора): id, name, alias, country, offer_id, status,
                  keitaro_campaign_id, keitaro_stream_ids, campaign_url, error, created_at, updated_at
```

- Рабочая версия: `status`, `weight`. Опубликованная (что сейчас в Keitaro): `published_status`, `published_weight`. `NULL` — привязка ни разу не публиковалась (добавлена в обёртке).
- У удалённого (`removed`) вес всегда 0.
- **Поток — черновик (жёлтый)**, если есть строка, где `(status, weight) != (published_status, published_weight)` (строка с `published_status = NULL` — всегда отличие).
- `is_pinned` — локальная настройка обёртки, Keitaro о ней не знает. Pin/unpin **не делает поток жёлтым** (кроме Unpin с пересчётом весов, когда сумма ≠ 100) и не откатывается Cancel.
- `offer_name` хранится в строке, чтобы архив показывался, даже если оффер стал недоступен. `sort_order` — порядок отображения и детерминированного распределения остатка.
- `has_offers` — поток показывается как поток с офферами, если в Keitaro у него есть офферы или у нас есть привязки. Потоки без офферов — только имя и позиция, содержимое не храним и не разбираем.

### 5.2. Правила весов — чистая функция
Вход: список `(status, is_pinned, weight)` в порядке `sort_order`. Выход: новые веса.

1. Удалённые → 0, в расчёте не участвуют.
2. `pinned_sum` = сумма весов закреплённых активных. Остаток `R = 100 − pinned_sum`.
3. `n` незакреплённых активных получают `R // n`, первые `R % n` из них (по `sort_order`) — ещё +1. Примеры: 4 оффера → 25/25/25/25; 3 → 34/33/33; закреплён 25 + два → 25/38/37.
4. Крайние случаи:
   - Закрепить оффер, если сумма закреплённых станет > 100 → отказ (422, «сумма закреплённых весов превысит 100%»).
   - `n = 0` и `pinned_sum ≠ 100` (все закреплены, сумма не 100) → веса не меняются, поток помечается проблемой «сумма весов N%, нужно 100% — открепите оффер», Push запрещён.
   - `n > 0` и `pinned_sum = 100` → незакреплённые получают 0%, это разрешено, но поток показывает предупреждение.

Пересчёт запускают **добавление, Remove, Bring back** и **Unpin, если сумма активных ≠ 100** (решение владельца, 2026-11-24). Pin, Fetch, Cancel веса не пересчитывают (Fetch берёт веса из Keitaro как есть, даже если сумма не 100).

### 5.3. Операции
- **Добавить оффер** — только в поток с офферами. Оффер должен существовать (кэш офферов). Если оффер уже активен в потоке → 409. Если он в архиве потока → работает как Bring back. Новая строка: `active`, `published_status=NULL`, в конец `sort_order`; пересчёт.
- **Remove** — `status=removed`, вес 0, закрепление снимается; пересчёт.
- **Bring back** — `status=active`; пересчёт.
- **Pin / Unpin** — переключает `is_pinned` (с проверкой суммы при pin); Unpin пересчитывает веса, только если сумма активных ≠ 100.
- **Cancel** — для каждой строки: `published_status=NULL` → строка удаляется (сам оффер в Keitaro не трогаем); иначе `status/weight := published_status/published_weight`. Откатываются и добавления, и удаления, и возвраты. Закрепления не трогаются.
- **Push to KT** — предусловия: поток — черновик; запись разрешена защитой по префиксу (5.6); если активные офферы есть — их сумма весов = 100. Поток без активных офферов публиковать **можно** (иначе с единственным оффером не проверить Remove → Push), но перед этим UI предупреждает «поток останется без офферов». Принимает ли Keitaro пустой список офферов — проверка этапа 1; если отвергнет, пользователь получит `keitaro_rejected` с текстом Keitaro. Затем:
  1. Читаем поток из Keitaro и сравниваем его офферы с опубликованной версией. Не совпадает → 409 «в Keitaro изменения, сначала Fetch Streams».
  2. Отправляем в Keitaro список активных офферов с весами (формат запроса — по итогам проверки этапа 1; меняются только офферы).
  3. Успех → опубликованная версия := рабочая для всех строк потока (удалённые: `published_status=removed`, `published_weight=0`). Поток белый.
  4. Ошибка Keitaro → наша БД не меняется, поток остаётся жёлтым, пользователь видит причину.

### 5.4. Fetch Streams
`GET /campaigns/{id}/streams`. Для каждого потока Keitaro:

- **Поток без черновика** — синхронизируется:
  - оффер есть в Keitaro и у нас → `active`, вес из Keitaro, опубликованная версия такая же;
  - оффер есть в Keitaro, у нас нет → новая строка `active` (опубликована);
  - оффер есть у нас (активный/опубликованный), в Keitaro нет → `removed`, вес 0, опубликованная версия тоже `removed` → поток **белый** (наше состояние совпадает с Keitaro), оффер серый с Bring back;
  - оффер в Keitaro в состоянии `disabled` → у нас `removed` (трафика не получает, как и серый);
  - закрепления сохраняются; вес закреплённого берётся из Keitaro.
- **Поток с черновиком** — по умолчанию **не трогаем**, в ответе предупреждение со списком таких потоков. Повторный Fetch с `force=true` отбрасывает черновики и синхронизирует.
- Потоки, которых больше нет в Keitaro, удаляются локально вместе с привязками.
- Порядок потоков — по `position` из Keitaro.

### 5.5. Выбор кампании
Список кампаний Keitaro с поиском по имени и id (фильтрация на нашем бэкенде; список кэшируется на короткое время). Просматривать и делать Fetch можно для любой кампании — это запись только в нашу БД.

### 5.6. Защита от записи в чужие кампании
`KEITARO_WRITE_NAME_PREFIX`: если задан, любые записи в Keitaro (создание кампании, Push) разрешены только для кампаний, чьё имя начинается с префикса; иначе 403 с понятным сообщением. В нашем `.env` — `test_oso4lq_`; пусто — без ограничений. Компенсация трогает только id, которые мы сами создали в этом же запросе.

## 6. Архитектура бэкенда

### 6.1. Слои
```
routers (HTTP, валидация, маппинг ошибок)
   → services (создаватор, редактор: синхронизация, операции, публикация)
       → domain (чистые функции: веса, переходы состояний, вычисление «черновика»)
       → keitaro (протокол KeitaroClient + реализация на httpx — единственное место, знающее формат Keitaro)
       → repositories (SQLAlchemy)
```
- Бизнес-логика — в services и domain; роутеры тонкие.
- `KeitaroClient` — интерфейс (Protocol). В тестах сервисов — in-memory фейк; HTTP-реализация тестируется отдельно с моком HTTP (respx).
- Схемы нашей API — свои (Pydantic), не копия Keitaro.
- Синхронный стек: обычные эндпоинты FastAPI, синхронные SQLAlchemy и `httpx.Client`.

### 6.2. Клиент Keitaro
- Таймаут и число повторов — из конфигурации (`KEITARO_TIMEOUT_SECONDS`, `KEITARO_MAX_RETRIES`). Повторы с паузой — только для GET и сетевых ошибок.
- Ошибки Keitaro → свои исключения → ответы нашей API с полями `code` и `message`:

| Ситуация | Наш ответ |
|---|---|
| Сеть, таймаут, 5xx | 502 `keitaro_unavailable` |
| 401 | 502 `keitaro_auth_failed` («неверный ключ API») |
| 402 | 502 `keitaro_license` |
| 403 | 403 `keitaro_forbidden` |
| 404 | 404 `keitaro_not_found` |
| 400/406/422 | 422 `keitaro_rejected` + текст Keitaro |

- Заголовок `Api-Key` не логируется никогда (фильтр логов и `repr` настроек скрывают ключ).

### 6.3. Наша API (черновой список; имена — на усмотрение исполнителя)
- `GET /api/countries`
- `GET /api/offers?query=` — поиск по id и подстроке названия
- `POST /api/campaigns` — создаватор; `GET /api/created-campaigns` — журнал
- `GET /api/keitaro-campaigns?query=` — выбор кампании для редактора
- `POST /api/editor/campaigns/{keitaro_id}/fetch?force=` и `GET /api/editor/campaigns/{keitaro_id}`
- `POST /api/editor/streams/{id}/offers` (добавить), `.../offers/{offer_id}/remove|bring-back|pin|unpin`
- `POST /api/editor/streams/{id}/push`, `POST /api/editor/streams/{id}/cancel`

Операции редактора возвращают полное представление потока: офферы с весами и статусами, `is_draft`, `can_push`, список проблем/предупреждений. Фронтенд только отображает.

### 6.4. Конфигурация (`.env`)
`KEITARO_BASE_URL`, `KEITARO_API_KEY`, `KEITARO_TIMEOUT_SECONDS`, `KEITARO_MAX_RETRIES`, `KEITARO_WRITE_NAME_PREFIX`, `DATABASE_URL`, `CAMPAIGN_DOMAIN`, `CAMPAIGN_GROUP`, `CAMPAIGN_TRAFFIC_SOURCE`, `REDIRECT_URL`, `OFFERS_CACHE_TTL_SECONDS`, `CORS_ORIGINS`. `KEITARO_ADMIN_LOGIN/PASSWORD` — только для ручных проверок через браузер, приложением не используются.

## 7. Фронтенд

- Две страницы: **Create** (Name, Geo — выпадающий список стран, Offer — поиск с автокомплитом, Create; результат или ошибка) и **Editor** (выбор кампании с поиском, Fetch Streams, список потоков).
- Поток: белый/жёлтый фон; у потока с офферами — таблица офферов (название, вес %, признак закрепления), кнопки Remove / Bring back / Pin / Unpin по строкам, добавление оффера с поиском, Push to KT и Cancel (активны только для черновика). Потоки без офферов — только имя.
- Удалённые офферы — серые, 0%, в блоке «архив» потока.
- Состояние — signals; всё для отображения (цвет, подписи, проценты, доступность кнопок) готовится заранее: ответ API → чистая функция-маппер → view-model → `computed`. В шаблонах только `@if/@for/@switch`, без вызовов методов и геттеров.
- Dev-сервер Angular проксирует `/api` на бэкенд.

## 8. Тестирование

## 9. Проверки на реальном Keitaro (только объекты `test_oso4lq_`)

- **Этап 1:** команда разведки (домены, группы, источники, офферы) работает. Создать тестовую кампанию `test_oso4lq_put_check` и выяснить семантику `PUT /streams/{id}`: можно ли слать только `offers`, заменяет ли список целиком, сохраняются ли фильтры/действие/позиция. Принимает ли Keitaro `share=0` и пустой список `offers`. Архивирует ли `DELETE /campaigns` потоки. Результаты — в `docs/decisions.md` и `docs/keitaro-examples/` (реальные запросы и ответы без секретов).
- **Этап 2:** в админке руками собирается эталонная кампания `test_oso4lq_reference` (те же домен, группа, источник, два потока по 4.2), затем она сравнивается **поле за полем** (кампания и оба потока, через API) с кампанией из создаватора. Всё, что админка подставляет сама (например, параметры из источника или настройки стоимости), создаватор тоже должен проставлять; расхождения устраняются или записываются в `docs/decisions.md`. Обе тестовые кампании после сравнения переносятся в архив. Эталон собран и разобран до плана этапа (2026-11-19, кампания 215193, примеры 23–24); приёмка — команда сравнения, которая только читает Keitaro, на кампании `test_oso4lq_creator_check`, созданной через нашу API.
- **Этап 3:** с оффером 18813 на тестовой кампании: Fetch, Remove → Push (оффер исчез из Keitaro, у нас серый), Bring back → Push, удаление оффера в Keitaro руками → Fetch (серый). После первого Push — проверка, что фильтры и прочие настройки потока не изменились.

## 11. Решения (кратко; полный журнал — `docs/decisions.md`)

| Вопрос | Решение |
|---|---|
| Хранение черновика | Вариант A — две версии в строке привязки (выбран владельцем) |
| Проверка на реальном Keitaro | Один оффер 18813; мульти-офферные сценарии — тестами (выбор владельца) |
| Округление весов | Целые; остаток по +1 первым незакреплённым по порядку |
| Крайние случаи pin | См. 5.2: pin > 100 запрещён; все закреплены и сумма ≠ 100 → Push запрещён; незакреплённые с 0% — предупреждение |
| Fetch при черновике | Не трогаем черновой поток, предупреждаем; `force=true` — отбросить |
| Cancel | Откатывает весь черновик потока (добавления, удаления, возвраты); pin не трогает |
| Pin и черновик | Pin — локальная настройка, поток не желтеет |
| Добавление в поток без офферов | Запрещено |
| Выбор кампании | Список из Keitaro с поиском |
| Гео в создаваторе | Одна страна из списка ISO 3166-1 alpha-2 |
| Тип потоков | Оба `regular`, позиции 1 и 2 (по эталону) |
| Push при изменениях в Keitaro | Отказ 409, нужен Fetch |
| Оффер удалён в Keitaro → Fetch | Серый, поток белый |
| `disabled` оффер в Keitaro | Считается удалённым |
| Защита общего Keitaro | `KEITARO_WRITE_NAME_PREFIX=test_oso4lq_` |
| Синхронный или асинхронный стек | Синхронный |
| Push потока без активных офферов | Разрешён с предупреждением в UI |
| «Совпадает с эталоном» | Сравнение поле за полем с кампанией, собранной руками в админке |
