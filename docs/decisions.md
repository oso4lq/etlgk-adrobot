Каждое решение — что выбрано и почему. Подробности устройства — в `docs/superpowers/specs/2026-11-18-adrobot-design.md`.
Пометка «владелец» — выбор владельца репозитория; остальное — решения исполнителя по принципу наименьшего сюрприза, согласованные вместе с дизайном.

## 2026-11-18 — разведка и дизайн

### Источник схем Keitaro
Папки `docs/keitaro-examples/` не было. Схемы берутся из спецификации Admin API v1 (`docs/keitaro-openapi.json`, получена из админки трекера) и из реальных ответов API. Реальные примеры запросов складываются в `docs/keitaro-examples/` на этапе 1 (без секретов).

### Доступ к Keitaro и ключ API
Ключ Admin API создан в профиле тестового пользователя, хранится только в `.env`. Доступы к админке из `CLAUDE.md` перенесены в `.env`, чтобы не попасть в открытый репозиторий.

### Проверка на реальном Keitaro — один оффер (владелец)
Тестовому пользователю виден один оффер (18813), создавать офферы нельзя (403). Вживую проверяется всё, что возможно с одним оффером; сценарии с несколькими офферами — тестами с подменённым клиентом Keitaro. Чужие и невидимые офферы не используем.

### Префикс тестовых объектов
Всё, что создаётся в общем Keitaro, называется с префиксом `test_oso4lq_`.

### Защита от записи в чужие кампании
Настройка `KEITARO_WRITE_NAME_PREFIX`: если задана, создание кампаний и Push разрешены только для кампаний с этим префиксом. В нашем `.env` — `test_oso4lq_`, пусто — без ограничений. Почему: инстанс общий, ошибка в обёртке не должна задеть чужие кампании.

### Хранение черновика — две версии в строке привязки (владелец)
У каждой привязки оффера к потоку есть рабочая версия (статус, вес) и опубликованная (что в Keitaro). Поток жёлтый, если они где-то различаются. Почему: Cancel и Push сводятся к копированию между версиями, все переходы — простые функции, легко тестировать. Отклонены: JSON-снимок потока (хуже прозрачность, архив приходится выводить) и журнал операций (избыточно).

### Округление весов
Вес оффера в Keitaro — целое число. Остаток `100 − сумма закреплённых` делится поровну между незакреплёнными активными, остаток от деления — по +1 первым по порядку отображения. 3 оффера → 34/33/33; закреплён 25 + два → 25/38/37. Почему: сумма всегда ровно 100, результат детерминирован.

### Крайние случаи закрепления
- Закрепить, если сумма закреплённых станет больше 100% — отказ с сообщением.
- Все активные закреплены и сумма не 100% — веса не меняются, поток помечен проблемой, Push запрещён до исправления.
- Закреплённые дают ровно 100%, а незакреплённые есть — они получают 0%, показывается предупреждение.

### Что запускает пересчёт весов
Только добавление, Remove и Bring back. Pin, unpin, Fetch и Cancel веса не пересчитывают; Fetch берёт веса из Keitaro как есть.

### Pin — локальная настройка
Keitaro о закреплении не знает, поэтому pin/unpin не делает поток жёлтым и не откатывается Cancel. Remove снимает закрепление.

### Cancel
Откатывает весь черновик потока: неопубликованные добавления удаляются (только привязка, оффер в Keitaro остаётся), удаления и возвраты отменяются.

### Добавление оффера
Только в потоки, где офферы уже есть. Оффер должен существовать среди видимых через API (Keitaro сам этого не проверяет). Уже активный оффер — отказ; оффер из архива потока — работает как Bring back.

### Push
- Предусловия: поток — черновик, разрешён защитой по префиксу, сумма весов активных офферов = 100 (если они есть).
- Поток без активных офферов публиковать можно, с предупреждением в UI. Почему: иначе с единственным оффером не проверить Remove → Push.
- Перед отправкой поток читается из Keitaro; если там офферы отличаются от опубликованной версии — отказ 409, нужен Fetch. Почему: не затирать чужие ручные правки молча.
- Меняются только офферы потока; формат запроса подтверждается реальной проверкой на этапе 1.
- Ошибка Keitaro не меняет нашу БД.

### Fetch Streams
- Потоки с черновиком не трогаются, пользователь получает предупреждение; Fetch с `force=true` отбрасывает черновики.
- Оффер удалён в Keitaro → у нас серый, поток белый (наше состояние совпадает с Keitaro).
- Оффер в Keitaro в состоянии `disabled` → у нас удалённый.
- Потоки, которых нет в Keitaro, удаляются локально вместе с привязками.

### Выбор кампании в редакторе
Список кампаний из Keitaro с поиском по имени и id.

### Создаватор
- Geo — одна страна из полного списка ISO 3166-1 alpha-2.
- Оба потока типа `regular` (как на эталонном скриншоте — у обоих ручка перетаскивания), «Flow 1» (страна → `https://google.com`) и «Flow 2» (все остальные → оффер, 100%).
- Alias — случайные 6 символов `[A-Za-z0-9]`, при конфликте — до 3 попыток.
- Компенсация при сбое — перенос созданного в архив Keitaro (`DELETE`). `clean_archive` не используется никогда — он чистит архив всех пользователей.
- Запросы на создание не повторяются автоматически (иначе дубли); повторы — только для чтения.
- «Совпадает с эталоном» — сравнение поле за полем с кампанией, собранной руками в админке (этап 2).

### Ручной ввод веса
Не делаем: в видео вес только закрепляется в текущем значении.

### Стек
Синхронный бэкенд (FastAPI, SQLAlchemy, httpx.Client) — проще читать и тестировать, нагрузка внутреннего инструмента невелика.

Глобально стоял Node 22.13.1, но через nvm уже был установлен 24.16.0 — фронтенд собран на Angular 22 под Node 24.16.0, версия закреплена в `frontend/.nvmrc` и `engines.node`. ### Запуск бэкенда через фабрику
`uvicorn app.main:create_app --factory`. Глобального экземпляра приложения нет, поэтому импорт кода не требует `.env` (тесты собирают приложение со своими настройками).

### Настройки миграций отдельно от настроек приложения
`DatabaseSettings` (только `DATABASE_URL`) — родитель `Settings`. Alembic использует `DatabaseSettings`, поэтому миграции работают без ключа Keitaro. Адрес базы в Alembic не проходит через configparser (знак `%` в пароле Postgres ломал бы миграции); тесты передают адрес через `Config.attributes`.

### Ошибки конфигурации без секретов
`hide_input_in_errors=True`: при пропущенной переменной ошибка называет переменную, но не печатает значения из `.env` (ключ API, пароль админки). `env_ignore_empty=True`: пустое `KEY=` считается незаданным — обязательная переменная падает при старте, необязательная получает значение по умолчанию.

### Базовая миграция
Пустая ревизия `0001` — точка, к которой цепляются таблицы этапов 2–3.

### httpx2 только для тестов
Starlette помечает `TestClient` поверх `httpx` устаревшим и предлагает `httpx2`. `httpx2` добавлен в dev-зависимости; приложение обращается к Keitaro через `httpx`, как требует `CLAUDE.md`.

### Build-скрипты pnpm запрещены
Angular CLI сгенерировал `allowBuilds: false` для esbuild и др. в `frontend/pnpm-workspace.yaml`. Оставлено как есть: нативные бинарники приходят через optionalDependencies, сборка, тесты и dev-сервер работают, а запрет postinstall-скриптов безопаснее.

## 2026-11-18 — этап 1 (клиент и разведка)

### Разведка реального Keitaro
Примеры — `docs/keitaro-examples/` (оглавление в `README.md` там же), получены одним запуском `python -m tools.keitaro_probe --confirm-writes`. Созданные кампания `test_oso4lq_put_check` и три потока перенесены в архив; кампания видна в `GET /campaigns/deleted` со `state: deleted`, потоки — `state: deleted`.

### В1. Тела создания
Тела 10, 12, 13, 14 приняты как есть (200). Keitaro сам подставил: кампании — `token`, `position` 9999, `cookies_ttl` 24, `cost_type` CPC, `cost_currency` USD, `uniqueness_method` ip, `bind_visitors` null, `postbacks` [], а также `domain` (`https://kylovoa.com/`) и `group` (имя) по id (10); потокам — `offer_selection` before_click, пустые `landings` и `triggers`, у фильтров и строк офферов — свои `id` и `stream_id`, у фильтров ещё `oid` (12–14). Ответ `POST /streams` короче, чем `GET /streams/{id}`: `action_options`, `action_payload` (у потока с офферами), `collect_clicks`, `filter_or`, `weight` видны только через GET (16, `stream_before`).

### В2. Занятый alias
`422 {"alias": ["Alias has already used"]}`, дубль не создаётся (11). На этапе 2 конфликт alias распознаётся по статусу 422 и ключу `alias` в теле.

### В3. PUT только с `offers`
Наблюдения: фильтры, `comments`, позиция, тип, схема, `action_type`, состояние и прочие поля не меняются; единственное отличие — `action_payload` `null` → `""` (16, `changed_fields`; ответ самого PUT ещё показывает `null`, следующий GET — `""`). Повторные PUT (17–19) кроме офферов ничего не меняют. Flow 2, созданный через API и ни разу не обновлённый, хранит `null` (22, `campaign_streams_after`). Выборка по 120 кампаниям инстанса (только чтение): из 100 потоков `landings` 69 хранят `""`, 31 — `null`.
Вывод (предположение, напрямую не проверялось): Keitaro приводит неиспользуемое `action_payload` потока `landings` к `""` при сохранении, вероятно при любом, включая админку; `null` остаётся у потоков, которые после создания через API не сохранялись. Поведение потока это не меняет.
Решение: Push шлёт только `{"offers": [...]}`. Условие остановки разведки для 16 считает `null` и `""` в `action_payload` одинаковыми; сырой `changed_fields` в файле 16 оставлен как доказательство.
Этап 3: при сверке потока после Push считать `null` и `""` в `action_payload` одинаковыми.

### В4. Замена списка офферов
PUT заменяет список целиком: `offers: []` убирает все офферы (18). Строка оффера сохраняет id, пока оффер остаётся в списке (16, 17 — тот же id, меняется только `share`); после удаления и повторного добавления создаётся новая строка с новым id (19). Сопоставлять офферы при синхронизации — по `offer_id`, не по id строки.

### В5. `share: 0`
Принимается: 200, оффер остаётся `active` с `share` 0 (17).

### В6. Пустой `offers`
Принимается: 200, у потока не остаётся офферов (18). Push потока без активных офферов возможен.

### В7. Удаление
- `DELETE /streams/{id}` → 200 с пустым телом; поток после этого читается, `state: deleted` (21).
- `DELETE /campaigns/{id}` → 200, тело — массив из одной кампании со `state: deleted`; `GET /campaigns/{id}` после этого → 404 (HTML nginx) (22).
- Потоки кампании при этом **не** архивируются: остаются `active` и видны через `GET /campaigns/{id}/streams` (22, `country_flow_after`, `campaign_streams_after`). Компенсация на этапе 2 архивирует потоки явно, до кампании.
- `GET /campaigns/{id}/streams` не возвращает архивные потоки: Probe (1323896, заархивирован в 21) есть в 15, но отсутствует в `campaign_streams_after`; для архивной кампании этот запрос по-прежнему отвечает 200 (22). Для этапа 3: Fetch Streams не видит потоки, заархивированные в Keitaro.

### Расхождения `docs/keitaro-openapi.json` с реальностью
- `DELETE /campaigns/{id}`: в спецификации 201 и объект Domain, на деле 200 и массив кампаний (22).
- `DELETE /streams/{id}`: в спецификации объект Stream, на деле пустое тело (21).
- Несуществующий id: 404 с HTML nginx, а не JSON `Error` (06, 22).
- Занятый alias: 422, в спецификации у `POST /campaigns` такого кода нет (11).
- У потока нет `updated_at`, есть `created_at` (16).
- `group_id` кампании в спецификации запроса — строка; число принимается (10).

### Транспорт Keitaro (задача 2)
- Мок HTTP — встроенный `httpx.MockTransport` вместо respx: лишняя зависимость не нужна, транспорт и так подменяется через конструктор.
- Отдельный фильтр логов для ключа не нужен: ключ есть только в заголовке внутреннего `httpx.Client`, наш код заголовки не логирует. Тест на уровне DEBUG покрывает наш код и логи httpx с `MockTransport`; httpcore этот транспорт обходит, поэтому им не проверено. Адрес трекера httpx пишет в лог на уровне INFO (`HTTP Request: GET https://...`), а httpcore на DEBUG — хост и имя сервера TLS, поэтому логгеры `httpx` и `httpcore` подняты до WARNING (проверяется тестом).
- Повторы: GET повторяется при сетевых ошибках, таймаутах и ответах 502/503/504; POST/PUT/DELETE — только если соединение не установлено (`ConnectError`, `ConnectTimeout`), чтобы не создать дубль. Число повторов — `KEITARO_MAX_RETRIES`.
- Ответ об ошибке не в JSON (HTML nginx) превращается в сообщение без текста Keitaro; ключ API в тексте Keitaro заменяется на `***`. Исходный текст исключений httpx в сообщения не попадает (в нём может быть адрес трекера).
- Ответ Keitaro, не подходящий под наши модели (пустое тело, `name: null` и т. п.), превращается в `KeitaroUnavailableError("Keitaro недоступен: некорректный ответ")` — тот же класс и текст, что у не-JSON ответа 2xx; в журнал попадают только пути полей. Для `create_*` это значит: объект в Keitaro мог создаться, а ответ не разобран; вызывающий код (компенсация этапа 2) должен это учитывать.
- Справочники из конфигурации: значение из одних цифр — поиск по id, иначе точное совпадение имени; пустое значение — не найдено; поэтому имя из одних цифр через конфиг указать нельзя — указывайте id.
- Данные в примерах (решение владельца): кроме секретов скрываются и чужие данные внутри наших объектов — у оффера название, группа, гео, партнёрская сеть, папка и пути лендинга; у домена — чужая кампания по умолчанию и группа. Маскируется только текст (`***`), структура и числовые id остаются, чтобы примеры показывали реальный формат ответа. Маскировка встроена в скрипт разведки, повторный запуск даёт те же файлы.

## 2026-11-19 — этап 2 (создаватор): эталон из админки

### Эталон `test_oso4lq_reference` (кампания 215193)
Собран руками в админке через браузер: домен `kylovoa.com`, группа и источник `FORTESTS`, всё остальное — значения админки по умолчанию; Flow 1 «Прямой URL» → `https://google.com`, фильтр «Страны принимать: Германия»; Flow 2 «Лендинги и офферы», оффер 18813, 100%. Админка сохраняет новые потоки только вместе с кампанией (кнопка «Сохранить»), сама пишет через внутренний RPC (`/admin/?batch`), а не через Admin API, поэтому сравнение идёт по результату, прочитанному через Admin API.

### Чем админка отличается от создания через API
По сравнению с кампанией этапа 1 (10, 12, 13, 22), если не считать id, alias, имени, token и дат:
- кампания: `uniqueness_method` `ip_ua` (через API по умолчанию `ip`), `cost_auto` `true` (через API `false`), `notes` и `uniqueness_param` — `""` (через API `null`);
- оба потока: `weight` 100 (через API 0), `comments` `""` (через API `null`).
Первые два меняют поведение (уникальность кликов, расход из параметра `cost`), остальные — нет, но «совпадает с эталоном» означает совпадение поле за полем.

### Тела создания с полями админки (24)
Создаватор шлёт в `POST /campaigns` дополнительно `cost_auto: true`, `uniqueness_method: "ip_ua"`, `uniqueness_param: ""`, `notes: ""`, а в `POST /streams` — `weight: 100`, `comments: ""`. Проверено реальным запросом (кампания `test_oso4lq_body_check`, сразу в архиве): Keitaro принял всё, результат совпал с эталоном без расхождений. `uniqueness_method` и `uniqueness_param` в спецификации `CampaignRequest` нет — ещё одно расхождение спецификации с реальностью. Значения взяты как константы тел (это значения по умолчанию админки, а не настройка пользователя).

### Уточнение к В3
Flow 2, созданный в админке, хранит `action_payload: null` (23). Значит, `""` появляется не при любом сохранении: создание через админку его не подставляет, подставляет `PUT` (16). Вывод В3 для этапа 3 не меняется: `null` и `""` сравниваются как равные.

### Список кампаний пропускает неразбираемые элементы
`list_campaigns` проверяет каждую кампанию по отдельности и пропускает те, что не подходят под нашу модель (например, `name: null`), записывая в журнал только их количество. Если тело ответа вообще не список — это по-прежнему «Keitaro недоступен: некорректный ответ». Почему: инстанс общий, и одна чужая кривая кампания не должна ломать поиск по alias при компенсации и выбор кампании в редакторе. Решение перенесено с этапа 3, потому что компенсации оно нужно уже сейчас.

### Список стран
Страны берутся из `pycountry` (ISO 3166-1 alpha-2, английские названия), а не из своей таблицы: не нужно поддерживать список вручную, а коды гарантированно стандартные. Ответ `GET /api/countries` — пары `{code, name}`.

### Поиск офферов
- Совпадение: префикс id или подстрока названия без учёта регистра; оффер с точным id идёт первым; результатов не больше 20; пустой запрос возвращает первые 20.
- Офферы кэшируются на `OFFERS_CACHE_TTL_SECONDS`: автокомплит шлёт запрос на каждую букву, а `GET /offers` в Keitaro тяжёлый.
- `OfferCatalog.find` (проверка оффера при создании кампании): промах принудительно обновляет кэш один раз, даже если он свежий, — только что созданный в Keitaro оффер должен проходить проверку. Цена — один лишний `GET /offers` на каждый неизвестный id. Если кэш только что загружен, повторной загрузки нет.

### Журнал созданных кампаний
Статусы записи: `pending` (создание идёт), `created`, `failed` (сбой, созданное убрано в архив), `compensation_failed` (часть созданного убрать не удалось, нужна ручная уборка). Идентификаторы потоков хранятся двумя столбцами (`country_stream_id`, `offers_stream_id`), а не списком: потоков ровно два, и столбцы проще читать и фильтровать. Запись сохраняется после каждого шага, чтобы при падении остались id для ручной уборки.

### Ответы об ошибках создавателя
Ответ любой ошибки нашей API — `{"code", "message"}`.
- `invalid_name` — 422; `name_prefix_required` — 422 (а не 403: запрос понятен, но не проходит проверку входных данных; префикс задаёт `KEITARO_WRITE_NAME_PREFIX`); `unknown_country` — 422; `offer_not_found` — 422.
- `creator_misconfigured` (домен, группа или источник из конфигурации не найдены в Keitaro) — 503; `compensation_failed` — 502; `internal_error` — 500 с фиксированным текстом «внутренняя ошибка»: текст неожиданного исключения может содержать что угодно, в том числе адрес трекера.
- Ошибки валидации запроса — `422 {"code": "invalid_request", "message": "Некорректный запрос: неверные или отсутствующие поля …"}`: наш обработчик вместо стандартного `{"detail": …}` у FastAPI, чтобы все ошибки API имели один формат. В сообщение попадают только имена полей, значения не попадают.
- Исчерпание попыток alias: «Кампания не создана: Не удалось подобрать свободный alias за 3 попытки» — тот же префикс «Кампания не создана», что и у остальных сбоев создания.

### Компенсация при сбое создания
- Если ответ на создание кампании неоднозначен (сеть, таймаут), кампания ищется в Keitaro по нашему alias; найденной считается только кампания с нашим alias и нашим (обрезанным) названием. Найденная убирается в архив. Не найдена — запись `failed` с текстом «Кампания не создана: <причина>. Кампания с alias <alias> в Keitaro не найдена». Сам поиск не удался — `compensation_failed` («проверить вручную»).
- Убираются все потоки кампании, прочитанные через `get_campaign_streams` (поток с потерянным ответом создания тоже), плюс известные нам id.
- Порядок: сначала потоки, потом кампания: архивация кампании оставляет её потоки активными.
- Повторять `POST /campaigns` автоматически нельзя; единственное исключение — новый alias после ответа «alias занят», максимум 3 попытки.
- Сбой записи в журнал после создания кампании обрабатывается как сбой потока: id кампании и потоков хранятся в памяти сразу после ответа Keitaro, всё созданное убирается в архив, ответ — `internal_error` (500). Компенсация идёт только по id, которые создатель держит в памяти (без чтения записи журнала); запись журнала обновляется после неё по возможности: если БД всё ещё недоступна, строка может остаться `pending`, результат — в тексте ошибки (с номером журнала) и в логе сервера. Причина: каждая кампания, оставленная в Keitaro, должна быть в журнале; если записать её нельзя, убираем. Это касается и последней записи со статусом `created`. Неудачный commit репозитория откатывает сессию; если не удалась и финальная запись об ошибке, это пишется в лог, а пользователь всё равно получает результат компенсации.

### Прочие правки итогового ревью
- Любое неожиданное исключение — `500 {"code": "internal_error", "message": "внутренняя ошибка"}`; неожиданная причина сбоя создания пишется в лог на уровне ERROR (`app.creator`).
- Тело запроса, которое не разобрано (битый JSON, не объект), — «Некорректный запрос: тело запроса не разобрано»; индексы в пути ошибки в имена полей не попадают.
- Название кампании — не длиннее 255 символов (размер столбца журнала); больше — `422 invalid_request` до обращений к Keitaro и записи в БД.
- Страны сортируются по названию без диакритики и регистра (NFKD, casefold): «Åland Islands» стоит рядом с «Albania». `list_countries()` каждый раз возвращает новый список.
- `compare_campaigns --record` скрывает и голый адрес трекера, не только полный URL.

## 2026-11-23 — этап 3 (редактор, бэкенд)

### `has_offers` вычисляется, а не хранится
Поток считается потоком с офферами, если у него есть хотя бы одна привязка. После Fetch поток с офферами в Keitaro всегда получает привязки; поток, у которого все офферы ушли в архив, остаётся потоком с офферами (с ним работают Bring back и добавление). Отличие от 5.1 спецификации: на один столбец меньше и не нужно поддерживать его согласованность.

### В адресах API — id из Keitaro
Кампания, поток и оффер в путях нашей API задаются id из Keitaro, а не нашими внутренними. Почему: они стабильны и видны пользователю в админке.

### Оффер `disabled` считается удалённым
Так сказано в спецификации. Push отправляет только активные офферы, поэтому после Push выключенный оффер исчезает из потока в Keitaro, а у нас остаётся в архиве потока и возвращается через Bring back. Слать `state: disabled` не проверяли, поэтому не шлём.

### Дубли оффера в одном потоке Keitaro
Через API один оффер можно добавить в поток дважды, а у нас уникальна пара `(stream_id, keitaro_offer_id)`. Дубли объединяются в одну привязку: она активна, если активна хотя бы одна строка; вес — сумма долей активных строк; порядок — по первому появлению. Почему: Fetch не должен падать на ограничении БД.

### Закреплённые из Keitaro в сумме больше 100
Fetch берёт веса как есть, поэтому закреплённые могут дать больше 100. Остаток считается как `max(0, 100 − сумма закреплённых)`, незакреплённые получают 0, отрицательных весов нет. Поток показывает проблему с текстом «открепите оффер», Push запрещён.

### Два вида проблемы «сумма не 100»
- Все активные закреплены или закреплённых больше 100: «Сумма весов N%, нужно 100% — открепите оффер».
- Веса пришли из Keitaro как есть: «Сумма весов N%, нужно 100% — веса пересчитаются при добавлении, удалении или возврате оффера».

Почему два текста: действие пользователя в этих случаях разное.

### Fetch переводит пропавший оффер в «удалён» и снимает закрепление
Оффер, которого больше нет в Keitaro, становится удалённым, а его закрепление снимается — как Remove в обёртке («как будто удалили руками», видео 04:46).

### Fetch и черновики
У потока-черновика без `force` обновляются только имя и позиция, офферы не трогаются. Поток, которого больше нет в Keitaro, удаляется локально даже с черновиком: опубликовать его всё равно некуда. Об этом выдаётся отдельное предупреждение с именами потоков, чьи изменения потеряны.

### Порядок проверок в Push
Сначала локальные проверки (черновик, сумма весов, префикс по сохранённому имени), затем чтение из Keitaro. Кампания в Keitaro не прошла проверку префикса по живому имени — 403 (кампанию могли переименовать после Fetch). Поток удалён или не найден — 409. Активные офферы в Keitaro уже совпадают с черновиком — публикация засчитывается без PUT: так повторный Push не застревает на 409, если ответ на PUT был потерян, а Keitaro его применил. Совпадают с опубликованной версией — PUT. Иначе — 409 «сначала Fetch». Порядок офферов при сравнении не учитывается.

### Состояние и повторные нажатия
Remove удалённого и Bring back активного — 409 `offer_state_conflict`. Pin и Unpin идемпотентны. Cancel потока без черновика ничего не меняет и отвечает 200. Push потока без черновика — 409 `stream_not_draft`.

### Remove оффера, добавленного без публикации
Работает как Remove любого другого: оффер серый, поток жёлтый. Cancel удаляет такую привязку совсем; после Push оффер остаётся в архиве потока. Особого случая не вводим: правил меньше, поведение предсказуемо.

### Имена офферов
Берутся из каталога офферов (кэш `GET /offers`). Если оффер не виден тестовому пользователю, показывается «Оффер {id}», а уже сохранённое имя не затирается.

### Выбор кампании
Поиск такой же, как у офферов: префикс id или подстрока имени, точный id первым, не больше 20. Новые кампании (больший id) сверху. Список кэшируется на 30 секунд — константой, а не переменной окружения: настройка здесь не нужна.

### Не делаем на этом этапе
- CORS-заголовки у ответа 500: фронтенд ходит через прокси `/api`, запрос не кросс-доменный.
- Авторизацию и блокировки: не цели дизайна.

### Принудительный Fetch и неопубликованные привязки
Принудительный Fetch оставляет неопубликованную привязку, если такой оффер уже есть в Keitaro, и перезаписывает её версиями Keitaro (иначе — конфликт уникальности и 500). Удаляются только неопубликованные привязки офферов, которых в Keitaro нет.

### Один источник чтения офферов потока
Офферы потока Keitaro читаются одной функцией `app/services/remote_offers.py` и в Fetch, и в Push. Почему: сверка перед записью корректна, только если правило «активен / доли / дубли» одинаково в обоих местах.

### Отказ Push не сохраняет имя кампании
При отказе Push (403) живое имя кампании не сохраняется: ошибка не меняет БД, редактор показывает старое имя до следующего Fetch.

### Коды ошибок редактора
Ответ — `{"code", "message"}` с указанным статусом.

| Код | HTTP | Текст |
|---|---|---|

| `pinned_sum_exceeds_100` | 422 | «Нельзя закрепить оффер {id}: сумма закреплённых весов станет {N}%, больше 100%» |
| `campaign_not_fetched` | 404 | «Кампания {id} ещё не загружена в редактор — выполните Fetch Streams» |
| `stream_not_found` | 404 | «Поток {id} не найден в редакторе — выполните Fetch Streams» |
| `offer_not_in_stream` | 404 | «Оффера {offer_id} нет в потоке {stream_id}» |
| `stream_without_offers` | 422 | «Поток {id} без офферов: добавлять офферы можно только в потоки, где они уже есть» |

| `offer_not_found` | 422 | «Оффер {id} не найден в Keitaro» (класс создавателя, перенесён в `offer_catalog`) |

Ошибки Keitaro (`keitaro_unavailable`, `keitaro_not_found`, `keitaro_rejected` и др.) пробрасываются как есть: их уже превращает в ответ общий обработчик `AppError`.

### Remove и Cancel снимают закрепление
Remove снимает закрепление (решение «Pin — локальная настройка»), а Cancel закрепления не трогает и не восстанавливает, поэтому после Remove → Cancel оффер возвращается с прежним весом, но незакреплённым. Почему так: закрепление — локальная настройка вне черновика; хранить «был закреплён до удаления» — лишний столбец ради редкого случая.

### Выключенный поток в Keitaro
Push публикует офферы и в выключенный (disabled) поток — меняются только офферы, поток остаётся выключенным; «поток удалён» — только `deleted`, 404 или поток другой кампании. Почему: иначе приостановленный поток становится тупиком (Fetch сохраняет черновик, Push отказывает). Попадает ли выключенный поток в `GET /campaigns/{id}/streams` — проверить при проверке на реальном Keitaro.

### Проверка на реальном Keitaro
Отложена: на 2026-11-23 Admin API трекера отвечает 403 (страница nginx) на любые запросы с этой машины, включая чтение; на этапах 1–2 те же запросы проходили. Ничего не записано. Проверка (Fetch, Remove → Push, Bring back → Push, удаление оффера в админке → Fetch, неизменность настроек потока после Push) будет выполнена после восстановления доступа.
